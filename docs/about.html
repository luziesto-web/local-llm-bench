Local LLM benchmark on a laptop GPU (8 GB)

An independent benchmark of open-weight models run locally through Ollama on one consumer laptop: which model and which settings (reasoning mode, temperature, context and reply budget) actually solve small coding tasks, and how long they take.

The goal: a local assembly line, not one "best model"

On 8 GB of VRAM no single model is both fast and reliable. One big model for every step is too slow; one small model for every step is too unreliable. So the benchmark is built around roles: one prompt goes in, a planner breaks it into steps, each step is delegated to the cheapest model that does that kind of step reliably, and a strong model checks the result. The levels below exist to find the right model and settings for each role.

The target line: one or two reliable Mastermind models for planning and checking, heavy but high-quality High executors, steady Medium executors, and light, fast Light/SuperLight workers for the many small steps - assembled into one cycle driven by a single prompt with efficient delegation. Between High and Mastermind sits a qualification level that decides who may be trusted with the checker role.

The final exam for High models (in preparation)

Short coding tasks show who can fix a module. The final exam shows who can build a whole product. Every High configuration gets the same brief: build a real, reusable team collaboration website from scratch - a Python server with a real database, not a mock-up - in ten consecutive stages, each in a fresh conversation with only a handoff note from its own previous stage. Accounts and sessions, shared workspaces with roles and access boundaries, work items with versioning and conflicting edits, comments, invitations, search and filters, a summary view, an accessible UI and demo data.

Each model family builds the same product under its own theme, so the sites cannot be copied from each other:

Findings so far

  1. Light tasks: Gemma 4 E4B and Qwen 3.5 4B tie (9/12 correct code) in the config matrix; for every model the vendor settings with reasoning on beat "no reasoning" and a "check yourself" system hint.
  2. Medium tasks: K2-Horizon 7B Q5 solved 13/15, Granite 4.2 8B and Qwen 3.5 9B 11/15 - Granite the fastest.
  3. The harness can be the bug: forcing JSON-formatted answers failed gpt-oss for reasons unrelated to coding; native tool calls fixed it. JSON is kept only where machine-readable output is the point of the task.
  4. A 12-minute cap per High episode loses nothing: every solved High episode finished within ~10 minutes; the failures ran 17-60 minutes. The cap cut 4-5 hours of a 14-hour night.
  5. gpt-oss "hangs" are reasoning, not stalls: at high effort it can think for 90+ s about copying a file that low effort writes in 5 s. Ollama's HTTP 500 is an intermittent "error parsing tool call", not memory. The harness was also dropping gpt-oss reasoning between tool calls (fixed).
  6. Less context can be better on 8 GB: K2 Q5 did best at 8K (Medium) and 12K (High) - more of the model stays in VRAM (26 vs 17 tokens/s at 24K).
  7. Check the task before blaming the model: a High task solved 0/29 times partly because its spec left the lease-expiry boundary open; the spec now states it and the checks report independent groups.

every task has hidden checks run on the files the model wrote (cases.py, light10_cases.py).

from measured token use; hard time limits per episode (High: 12 min); a time-out is a model outcome.
